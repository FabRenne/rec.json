Le projet fil rouge : « Mes tâches »

Une application de gestion de tâches (to-do list) qui permet de :

  • ajouter, cocher, supprimer des tâches ;
  • classer les tâches par catégorie (relation 1-N) ;
  • rechercher une tâche par son titre en temps réel ;
  • afficher le nombre de tâches restantes, mis à jour automatiquement.

1Introduction à Room

Room est la bibliothèque officielle de persistance d'Android (famille Android Jetpack). C'est une couche d'abstraction au-dessus de SQLite, la base de données relationnelle embarquée dans chaque appareil Android.

Pourquoi ne pas utiliser SQLite directement ?

SQLite « brut » (SQLiteOpenHelper)Room
Beaucoup de code répétitif (Cursor, ContentValues…)Annotations : le code est généré automatiquement
Erreurs SQL découvertes à l'exécution (crash)Requêtes vérifiées à la compilation
Conversion manuelle ligne ↔ objetConversion automatique en data class Kotlin
Pas de notification de changementRequêtes observables via Flow
Gestion des threads à la mainSupport natif des coroutines (suspend)
Migrations difficiles à testerSchéma exporté en JSON + outils de test

Quand utiliser Room ?

  • Données structurées et nombreuses (listes, historiques, catalogues…).
  • Mode hors-ligne : cache local de données venant d'une API.
  • Besoin de requêtes (filtres, tris, jointures, agrégats).
💡 Et DataStore ?Pour quelques préférences simples (thème sombre, langue, token…), préférez DataStore. Room est fait pour des données relationnelles.

3Les trois briques de Room

Room repose sur trois composants, chacun déclaré par une annotation :

BriqueType KotlinRôle
Entitydata classDécrit une table : chaque propriété devient une colonne.
DAOinterfaceDécrit les opérations (SQL) ; Room écrit l'implémentation.
Databaseabstract classRelie le tout, crée le fichier SQLite et fournit les DAO.

4Les entités (@Entity)

Une entité est une data class annotée par @Entity. Room crée une table dont les colonnes correspondent aux propriétés.

Les annotations essentielles

L'entité Tache du projet

data/local/entity/Tache.ktenum class Priorite { BASSE, NORMALE, HAUTE }

@Entity(
    tableName = "taches",
    foreignKeys = [
        ForeignKey(
            entity = Categorie::class,
            parentColumns = ["id"],
            childColumns = ["categorie_id"],
            onDelete = ForeignKey.CASCADE
        )
    ],
    indices = [Index("categorie_id")]   // un index sur chaque clé étrangère
)
data class Tache(
    @PrimaryKey(autoGenerate = true)
    val id: Long = 0,                   // 0 = "pas encore inséré"
    val titre: String,
    val description: String = "",
    @ColumnInfo(name = "est_terminee", defaultValue = "0")
    val estTerminee: Boolean = false,
    val priorite: Priorite = Priorite.NORMALE,
    @ColumnInfo(name = "date_echeance")
    val dateEcheance: LocalDate? = null,
    @ColumnInfo(name = "categorie_id")
    val categorieId: Long? = null,
    @ColumnInfo(name = "cree_le", defaultValue = "0")
    val creeLe: Long = System.currentTimeMillis()
) {
    @Ignore   // propriété calculée, jamais stockée
    val estEnRetard: Boolean =
        !estTerminee && dateEcheance != null && dateEcheance.isBefore(LocalDate.now())
}
💡 autoGenerate et la valeur 0Avec autoGenerate = true, si l'id vaut 0, Room laisse SQLite générer un nouvel identifiant. La méthode @Insert renvoie alors l'id créé (Long).

Exemple : @Embedded

    val nom: String,

5Les DAO (@Dao)

Un DAO (Data Access Object) est une interface qui déclare les opérations sur la base. Vous écrivez les signatures ; Room génère le code (classe TacheDao_Impl).

Les annotations de méthode

AnnotationEffetRetour possible
@InsertINSERT d'un ou plusieurs objetsLong (id) / List<Long>
@UpdateUPDATE par clé primaireInt (lignes modifiées)
@DeleteDELETE par clé primaireInt
@UpsertINSERT, ou UPDATE si la clé existeUnit / Long
@Query("…")N'importe quelle requête SQLObjet, liste, Flow, scalaire…
@TransactionExécute en une transaction atomique—

suspend ou Flow ?

data/local/dao/TacheDao.kt@Dao
interface TacheDao {

    // ---------- Écriture : fonctions suspend ----------
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun inserer(tache: Tache): Long

    @Insert
    suspend fun insererTout(taches: List<Tache>): List<Long>

    @Update
    suspend fun modifier(tache: Tache): Int

    @Upsert
    suspend fun enregistrer(tache: Tache)

    @Delete
    suspend fun supprimer(tache: Tache): Int

    @Query("UPDATE taches SET est_terminee = :terminee WHERE id = :id")
    suspend fun changerEtat(id: Long, terminee: Boolean)

    @Query("DELETE FROM taches WHERE est_terminee = 1")
    suspend fun supprimerTerminees(): Int

    // ---------- Lecture réactive : Flow ----------
    @Query("SELECT * FROM taches ORDER BY est_terminee ASC, priorite DESC, cree_le DESC")
    fun observerToutes(): Flow<List<Tache>>

    @Query("SELECT * FROM taches WHERE titre LIKE '%' || :texte || '%' ORDER BY cree_le DESC")
    fun rechercher(texte: String): Flow<List<Tache>>

    @Query("SELECT COUNT(*) FROM taches WHERE est_terminee = 0")
    fun compterRestantes(): Flow<Int>

    // ---------- Lecture ponctuelle ----------
    @Query("SELECT * FROM taches WHERE id = :id")
    suspend fun trouverParId(id: Long): Tache?

    // ---------- Transaction ----------
    @Transaction
    suspend fun remplacerTout(taches: List<Tache>) {
        toutSupprimer()
        insererTout(taches)
    }

    @Query("DELETE FROM taches")
    suspend fun toutSupprimer()
}

Paramètres de requête

Dans @Query, :nom fait référence au paramètre de la fonction du même nom. Room le lie de façon sécurisée (pas d'injection SQL). On peut aussi passer une collection :

@Query("SELECT * FROM taches WHERE id IN (:ids)")
suspend fun trouverPlusieurs(ids: List<Long>): List<Tache>

Stratégies de conflit (OnConflictStrategy)

StratégieSi la clé (ou un index unique) existe déjà…
ABORT (défaut)Annule l'opération et lève une exception
REPLACESupprime l'ancienne ligne puis insère la nouvelle (⚠ déclenche les CASCADE !)
IGNORENe fait rien ; @Insert renvoie -1
💡 Vérification à la compilationSi vous écrivez SELECT * FROM tache (sans « s ») ou une colonne inexistante, le projet ne compile pas : « There is a problem with the query: no such table: tache ». C'est l'un des gros atouts de Room.

6La classe RoomDatabase

La base est une classe abstraite qui hérite de RoomDatabase. Elle liste les entités, porte le numéro de version et expose les DAO via des fonctions abstraites.

data/local/AppDatabase.kt@Database(
    entities = [Tache::class, Categorie::class],
    version = 2,
    exportSchema = true
)
@TypeConverters(Converters::class)
abstract class AppDatabase : RoomDatabase() {

    abstract fun tacheDao(): TacheDao
    abstract fun categorieDao(): CategorieDao

    companion object {
        @Volatile
        private var INSTANCE: AppDatabase? = null

        fun getInstance(context: Context): AppDatabase =
            INSTANCE ?: synchronized(this) {
                INSTANCE ?: Room.databaseBuilder(
                    context.applicationContext,
                    AppDatabase::class.java,
                    "taches.db"
                )
                    .addMigrations(MIGRATION_1_2)
                    .build()
                    .also { INSTANCE = it }
            }
    }
}

Pourquoi un singleton ?

Ouvrir une base SQLite est coûteux, et plusieurs instances simultanées risquent des incohérences. On garantit donc une instance unique :

  • @Volatile : toutes les threads voient immédiatement la valeur écrite ;
  • synchronized : deux threads ne peuvent pas créer la base en même temps (double-checked locking) ;
  • applicationContext : évite une fuite mémoire de l'Activity.

Où créer la base ? Dans la classe Application

TacheApplication.ktclass TacheApplication : Application() {
    val database: AppDatabase by lazy { AppDatabase.getInstance(this) }
    val repository: TacheRepository by lazy {
        TacheRepository(database.tacheDao(), database.categorieDao())
    }
}
// + android:name=".TacheApplication" dans AndroidManifest.xml

7Les TypeConverters

SQLite ne connaît que 4 types de stockage : INTEGER, REAL, TEXT, BLOB. Room gère nativement les types primitifs, String, ByteArray et les enum. Pour les autres (dates, listes, objets…), on écrit des convertisseurs.

data/local/converter/Converters.ktclass Converters {

    @TypeConverter
    fun fromLocalDate(date: LocalDate?): Long? = date?.toEpochDay()

    @TypeConverter
    fun toLocalDate(jours: Long?): LocalDate? = jours?.let(LocalDate::ofEpochDay)

    @TypeConverter
    fun fromPriorite(p: Priorite): String = p.name

    @TypeConverter
    fun toPriorite(valeur: String): Priorite = Priorite.valueOf(valeur)
}

On enregistre ensuite la classe sur la base : @TypeConverters(Converters::class) (portée globale). On peut aussi la placer sur une entité, un DAO ou un champ pour limiter sa portée.

Exemple : stocker une liste de chaînes

class ListeConverter {
    @TypeConverter
    fun fromList(liste: List<String>): String = liste.joinToString(separator = "|")

    @TypeConverter
    fun toList(texte: String): List<String> =
        if (texte.isEmpty()) emptyList() else texte.split("|")
}
⚠️ AttentionStocker une liste dans une seule colonne empêche de faire des requêtes dessus (filtrer par étiquette…). Si vous devez interroger ces valeurs, créez plutôt une table séparée et une relation (chapitre suivant).

8Relations entre tables

Room ne permet pas à une entité de contenir directement une liste d'autres entités (pour éviter le chargement paresseux caché sur le thread UI). On modélise donc les relations avec des clés étrangères et des classes de relation.

1. La clé étrangère (dans l'entité enfant)

Voir l'entité Tache (chapitre 4) : ForeignKey(entity = Categorie::class, parentColumns = ["id"], childColumns = ["categorie_id"], onDelete = CASCADE). SQLite garantit alors qu'une tâche ne peut pas référencer une catégorie inexistante, et la suppression d'une catégorie supprime ses tâches.

2. La classe de relation (@Embedded + @Relation)

data/local/entity/CategorieAvecTaches.ktdata class CategorieAvecTaches(
    @Embedded
    val categorie: Categorie,                 // le parent

    @Relation(
        parentColumn = "id",                  // colonne de Categorie
        entityColumn = "categorie_id"         // colonne de Tache
    )
    val taches: List<Tache>                    // les enfants
)

3. La requête dans le DAO

data/local/dao/CategorieDao.kt (extrait)@Transaction   // Room exécute 2 requêtes : il faut un résultat cohérent
@Query("SELECT * FROM categories ORDER BY nom")

9Architecture MVVM : Repository & ViewModel

Google recommande une architecture en couches. L'UI Compose ne parle jamais directement à Room : elle passe par un ViewModel, qui passe par un Repository.

Le Repository

data/repository/TacheRepository.ktclass TacheRepository(
    private val tacheDao: TacheDao,
    private val categorieDao: CategorieDao
) {
    val taches: Flow<List<Tache>> = tacheDao.observerToutes()
    val categories: Flow<List<Categorie>> = categorieDao.observerToutes()
    val nombreRestantes: Flow<Int> = tacheDao.compterRestantes()

    fun rechercher(texte: String) = tacheDao.rechercher(texte)

    suspend fun ajouter(tache: Tache): Long = tacheDao.inserer(tache)
    suspend fun basculer(tache: Tache) = tacheDao.changerEtat(tache.id, !tache.estTerminee)
    suspend fun supprimer(tache: Tache) = tacheDao.supprimer(tache)
    suspend fun nettoyer(): Int = tacheDao.supprimerTerminees()
}

Le ViewModel

ui/TacheViewModel.ktdata class TachesUiState(
    val taches: List<Tache> = emptyList(),
    val categories: List<Categorie> = emptyList(),
    val recherche: String = "",
    val restantes: Int = 0,
    val chargement: Boolean = true
)

class TacheViewModel(private val repository: TacheRepository) : ViewModel() {

    private val recherche = MutableStateFlow("")

    // à chaque frappe, on annule l'ancienne requête et on en lance une nouvelle
    private val tachesFiltrees = recherche.flatMapLatest { texte ->
        if (texte.isBlank()) repository.taches else repository.rechercher(texte)
    }

    val uiState: StateFlow<TachesUiState> = combine(
        tachesFiltrees, repository.categories, repository.nombreRestantes, recherche
    ) { taches, categories, restantes, texte ->
        TachesUiState(taches, categories, texte, restantes, chargement = false)
    }.stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = TachesUiState()
    )

    fun onRechercheChange(texte: String) { recherche.value = texte }

    fun ajouter(titre: String, priorite: Priorite, categorieId: Long?) {
        if (titre.isBlank()) return
        viewModelScope.launch {
            repository.ajouter(Tache(titre = titre.trim(), priorite = priorite,
                                     categorieId = categorieId))
        }
    }

    fun basculer(tache: Tache) = viewModelScope.launch { repository.basculer(tache) }
    fun supprimer(tache: Tache) = viewModelScope.launch { repository.supprimer(tache) }

    companion object {
        val Factory = viewModelFactory {
            initializer {
                val app = this[APPLICATION_KEY] as TacheApplication
                TacheViewModel(app.repository)
            }
        }
    }
}
ÉlémentPourquoi ?
viewModelScope.launchLance les appels suspend ; annulé automatiquement quand le ViewModel est détruit.
stateIn(...)Transforme le Flow « froid » de Room en StateFlow « chaud » avec une valeur courante.
WhileSubscribed(5_000)Garde la requête active 5 s après la disparition de l'UI : une rotation d'écran ne relance pas la requête.
combineFusionne plusieurs flux en un seul état d'écran.
flatMapLatestChange de requête Room quand le texte recherché change.
FactoryPermet de passer le Repository au constructeur du ViewModel.
ℹ️ Et les threads ?Pas besoin de withContext(Dispatchers.IO) : les fonctions suspend et les Flow générés par Room s'exécutent déjà sur un exécuteur en arrière-plan. On peut donc les appeler depuis viewModelScope (thread principal) sans bloquer l'UI.

10Afficher les données avec Compose

Collecter l'état : collectAsStateWithLifecycle

collectAsStateWithLifecycle() (bibliothèque lifecycle-runtime-compose) transforme un StateFlow en State Compose. Chaque nouvelle valeur provoque une recomposition. La collecte s'arrête automatiquement quand l'application passe en arrière-plan.

Séparer composable « avec état » et « sans état »

ui/screens/TachesScreen.kt (extrait)// 1. Route : connaît le ViewModel

11Le cycle réactif complet

Voici ce qui se passe quand l'utilisateur coche une tâche. Aucune ligne de code ne « rafraîchit » la liste : Room s'en charge grâce à son InvalidationTracker.

À retenir : l'UI n'est jamais modifiée « à la main » après une écriture. On écrit dans la base, puis on laisse le Flow propager la nouvelle vérité. Ce principe s'appelle Single Source of Truth (source unique de vérité).

12Les migrations

Quand vous modifiez une entité (nouvelle colonne, nouvelle table…), le schéma de la base change. Les utilisateurs ont déjà une base dans l'ancienne version : il faut la migrer sans perdre leurs données.

Méthode 1 : migration manuelle

  1. Modifier l'entité (ajout de creeLe).
  2. Incrémenter version = 2 dans @Database.
  3. Écrire l'objet Migration avec le SQL nécessaire.
  4. L'enregistrer avec .addMigrations(MIGRATION_1_2).
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE taches ADD COLUMN cree_le INTEGER NOT NULL DEFAULT 0")
    }
}
⚠️ Le SQL doit correspondre exactement à l'entitéRoom compare le schéma obtenu après migration avec le schéma attendu. Ici l'entité déclare @ColumnInfo(name = "cree_le", defaultValue = "0") et un type Long non-null : il faut donc INTEGER NOT NULL DEFAULT 0. Sinon : IllegalStateException: Migration didn't properly handle…

Méthode 2 : AutoMigration

Pour les changements simples (ajout de colonne/table), Room peut générer la migration à partir des schémas exportés :

@Database(
    entities = [Tache::class, Categorie::class],
    version = 3,
    autoMigrations = [
        AutoMigration(from = 2, to = 3),
        // renommage : il faut aider Room avec une spec
        AutoMigration(from = 3, to = 4, spec = AppDatabase.RenommageSpec::class)
    ]
)
abstract class AppDatabase : RoomDatabase() {
    @RenameColumn(tableName = "taches", fromColumnName = "titre", toColumnName = "intitule")
    class RenommageSpec : AutoMigrationSpec
}

Prérequis : exportSchema = true et room.schemaLocation configuré. Les fichiers schemas/…/1.json, 2.json… doivent être versionnés dans Git.

Méthode 3 : migration destructive

.fallbackToDestructiveMigration(dropAllTables = true)
⛔ À réserver au développementToutes les données de l'utilisateur sont effacées. Acceptable uniquement pour un simple cache réseau qu'on peut re-télécharger.

Les tests de DAO sont des tests instrumentés (dossier androidTest) car ils utilisent le vrai SQLite d'Android. On utilise une base en mémoire, recréée pour chaque test.

class TacheDaoTest {

    private lateinit var db: AppDatabase
    private lateinit var tacheDao: TacheDao
    private lateinit var categorieDao: CategorieDao

    fun creerBase() {
        val context = ApplicationProvider.getApplicationContext<Context>()

            .allowMainThreadQueries()
            .build()
        tacheDao = db.tacheDao()
        categorieDao = db.categorieDao()
    }

    @After
    fun fermerBase() = db.close()

    @Test
    fun insererPuisLire() = runTest {
        val id = tacheDao.inserer(Tache(titre = "Réviser Room"))
        assertEquals("Réviser Room", tacheDao.trouverParId(id)?.titre)
    }

    @Test
    fun flowEmetApresInsertion() = runTest {
        tacheDao.inserer(Tache(titre = "A"))
        tacheDao.inserer(Tache(titre = "B"))
        assertEquals(2, tacheDao.observerToutes().first().size)
    }

    @Test

14Bonnes pratiques & erreurs fréquentes

✅ Bonnes pratiques

  • Une seule instance de la base (singleton ou @Singleton Hilt).
  • Écritures en suspend, lectures affichées en Flow.
  • Ne jamais accéder à Room depuis un @Composable : passer par le ViewModel.
  • Exposer un StateFlow d'état d'écran unique (UiState).
  • Utiliser collectAsStateWithLifecycle() plutôt que collectAsState().
  • Toujours fournir key = { it.id } dans les LazyColumn.
  • Indexer les colonnes de clés étrangères et celles souvent filtrées.
  • Utiliser @Transaction pour les opérations multiples et les @Relation.
  • Versionner les schémas exportés et tester les migrations.
  • Sélectionner seulement les colonnes utiles (projection) pour les grosses tables.
  • Pour des listes très longues : Paging 3 (PagingSource<Int, Tache> renvoyée par le DAO).

// ViewModel
private val _derniereSupprimee = MutableStateFlow<Tache?>(null)
val derniereSupprimee = _derniereSupprimee.asStateFlow()

fun supprimer(tache: Tache) = viewModelScope.launch {
    repository.supprimer(tache)
    _derniereSupprimee.value = tache
}
fun annulerSuppression() = viewModelScope.launch {
    _derniereSupprimee.value?.let { repository.ajouter(it) }   // même id → ré-insertion
    _derniereSupprimee.value = null
}

// Compose
val snackbar = remember { SnackbarHostState() }
val supprimee by vm.derniereSupprimee.collectAsStateWithLifecycle()
LaunchedEffect(supprimee) {
    if (supprimee != null) {
        val res = snackbar.showSnackbar("Tâche supprimée", actionLabel = "ANNULER")
        if (res == SnackbarResult.ActionPerformed) vm.annulerSuppression()
    }
}
